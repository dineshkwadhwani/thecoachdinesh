Study Guide

Start with the cloud model

Cloud security is different because organizations consume infrastructure and platforms they do not physically operate, while teams can create and change resources at software speed. The cloud provider secures parts of the underlying service; the customer remains accountable for its data, identities, access policies, and configuration.

Service model matters. With IaaS, the customer manages more of the stack, including guest operating systems and workloads. With PaaS, the provider also operates much of the platform and runtime. With SaaS, the provider operates the application, while the customer still manages users, data, and settings. The exact boundary varies by provider and service.

Lecture 1 · Foundations

The shared responsibility model

The provider is responsible for security of the cloud; customers are responsible for security in the cloud. Managed services move operational work to the provider, but do not make customer configuration and identity controls disappear.

Control areaProvider responsibilityCustomer responsibility
Physical facilitiesData-center access, physical protection, and underlying hardware.Select appropriate services and manage account access.
Compute and platformUnderlying infrastructure; more platform/runtime operation in managed services.Guest OS, application code, workload settings, and patching where the chosen service assigns them to the customer.
Identity and accessProvide identity and access capabilities.Configure accounts, least-privilege permissions, authentication, and MFA.
Data and configurationProvide storage and security features.Classify and protect data; set access policies, encryption options, and retention appropriately.
Case study · Capital One, 2019: The course uses this breach to show how a customer-side WAF configuration and excessive permissions can expose cloud data. The lesson is not that the provider has no role; it is that using a secure cloud does not remove customer responsibility for configuration and identity.

Five cloud security pillars

  • Identity and access management: least privilege and strong authentication.
  • Data protection: classification, encryption at rest and in transit, and tokenization.
  • Network security: segmentation, VPCs, and security-group rules.
  • Compliance and governance: controls, policy ownership, and evidence.
  • Monitoring, detection, and response: logs, alerts, and continuous posture checks.
Lecture 1 · Continuous Posture

CSPM: find configuration risk continuously

Cloud Security Posture Management (CSPM) tooling discovers cloud resources, checks configurations against policy and security baselines, and surfaces or helps remediate risk across accounts. It addresses three conditions that make manual review hard to sustain: high resource volume, rapid infrastructure changes, and configuration drift.

  1. Discover cloud resources and accounts so the inventory is current.
  2. Assess configurations against best practices, policy, and compliance requirements.
  3. Prioritize findings by exposure, impact, and context.
  4. Remediate through an owner, a change, or an approved automated fix.
  5. Monitor for drift and verify that the fix remains in place.

This is a loop, not a one-time audit. A resource that passed review yesterday may become exposed after a later deployment or manual change.

Know the neighboring tools

CapabilityQuestion it answersTypical focus
CSPMIs this cloud resource configured securely?Cloud configuration and posture.
CWPPIs this running workload behaving securely?Protection of workloads such as VMs and containers.
CIEMDoes this identity have more access than it needs?Permissions and cloud entitlements.

Common frameworks represented in CSPM policy libraries include CIS Benchmarks, PCI-DSS, ISO/IEC 27001, the RBI IT Framework, and India's DPDP Act, 2023. The mapping helps teams assess controls; it does not by itself guarantee compliance.

Lecture 2 · Identity

Single Sign-On and its three actors

Single Sign-On (SSO) lets a user authenticate once with a trusted Identity Provider and access multiple connected applications without independently signing in to each one. This can reduce password reuse and simplify account lifecycle management, while making protection of the identity provider especially important.

  • User: the person seeking access.
  • Identity Provider (IdP): verifies the user and issues a trusted identity signal.
  • Service Provider (SP), or relying party: the application that accepts that signal and creates an application session.
Keep these questions separate: Authentication asks “Who are you?” Authorization asks “What are you allowed to do?” OAuth 2.0 is fundamentally an authorization framework; OpenID Connect adds an identity layer for sign-in.

SAML 2.0 · enterprise sign-in

SAML is an XML-based protocol commonly used for enterprise SSO. Its core artifact is a signed assertion describing the authenticated user and relevant attributes.

  1. The user opens a service provider such as an HR application.
  2. The service provider redirects the browser to the organization’s IdP.
  3. The user authenticates at the IdP, with MFA when configured.
  4. The IdP returns a signed SAML assertion through the browser.
  5. The service provider validates the assertion and starts its session.

OAuth 2.0 · delegated, limited access

OAuth lets a user grant an application limited access to a resource held by another service without sharing the user’s password. In the authorization-code flow, the app receives a short-lived, single-use code, then exchanges it for tokens over a back-channel. Requested scopes should be limited to the access the app actually needs. PKCE protects public clients that cannot safely hold a client secret.

OpenID Connect · sign-in identity over OAuth

OpenID Connect (OIDC) builds on OAuth 2.0 and adds a signed ID token, commonly a JWT, for the client to establish the user’s identity. A JWT contains a header, claims payload, and signature. The client validates the token and its claims using the IdP’s published verification keys and protocol rules.

Risk & Controls

Protect the identity path

RiskWhy it mattersMitigation from the course

MFA and SSO are complementary. SSO centralizes authentication and policy; MFA adds an additional verification factor. Banking examples in the course use step-up checks such as a UPI PIN or biometrics for sensitive transactions.

Practice & Review

Four classroom exercises

1 · Whose responsibility is it?

Classify physical server firmware, storage bucket access, admin MFA, customer-data encryption, and data-center physical protection as provider, customer, or shared responsibility. Explain which service model could change the boundary.

2 · Spot the misconfiguration

Review a customer-export bucket with public read/list access, encryption and logging disabled, versioning disabled, and an AdministratorAccess role. Identify the immediate exposure, a control that reduces impact, and the excessive permission.

Review the expected reasoning for Exercise 2

Block public access first because the data is actively exposed. Encryption at rest reduces impact if data is accessed, but does not make a public bucket private. The broad administrator role should be replaced with the minimum permissions the workload needs; logging and versioning improve detection and recovery.

3 · Map the OAuth authorization-code flow

Fill in the key steps: the user starts in the client app/service provider; the IdP returns a short-lived authorization code; the client exchanges it over a back-channel; OIDC adds the ID token that identifies the user.

Check the Exercise 3 answers

Client App / Service Provider; authorization code; back-channel; OpenID Connect ID token (JWT).

4 · True or false?

Is OAuth 2.0 alone the right protocol for user login? Can a JWT signature be verified without calling the IdP for every request? Are MFA and SSO redundant?

Check the Exercise 4 answers

OAuth alone for login: false; OIDC adds the identity layer. JWT signature verification without a per-request IdP call: true when the token is validated correctly using trusted keys and claims. MFA and SSO redundant: false; they address different parts of the access flow.

Before you leave

  • Draw the shared responsibility model from memory.
  • Explain CSPM, CWPP, and CIEM in one sentence each.
  • Whiteboard the OAuth authorization-code flow.
  • Explain why OAuth alone does not establish a user’s identity.
